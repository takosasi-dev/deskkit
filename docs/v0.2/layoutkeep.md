# LayoutKeep v0.2.0 の変更点(仕様書との差分・理由・既定値)

対象: `deskkit/modules/layoutkeep/**`。契約は `docs/INTERFACES_v0.2.md`。逸脱不可要件(INV-1〜10)と C-1〜C-12 は変えていない。

## 0. まとめ

| 項目 | 既定値 | 自動で何かを動かすか |
|---|---|---|
| L1 名前付きプリセット | 既存データはそのまま読める(初めて書くときに移行) | 動かさない(データの形だけ) |
| L2 自動スナップショット | **オン**(10 分落ち着いたら1回、以後 30 分ごと) | 動かさない(DeskKit のデータを書くだけ) |
| L3 新しいウィンドウの配置 | **オフ**・オンにしても**試運転**から | 利用者が「本番」にし、かつ全体の mode も live のときだけ |
| スヌーズ | 本体の `ctx.is_snoozed()` を見る | 自動の処理だけ止める |
| `diagnostics()` | 追加 | — |

## 1. L1 名前付きプリセット(スコープ変更)

**仕様書からの変更**: §3 スコープ「構成シグネチャごとに1レイアウト」と D-2 前半(「レイアウトは構成シグネチャごとに1つ」)を、
「構成シグネチャごとに名前付きのプリセットを複数持ち、そのうち1つを既定にする」に変えた。
D-2 後半(**シグネチャが完全一致したときだけ適用**・近い構成への比例変換はしない)と INV-3 はそのまま。

- 例: 同じ「自宅2画面」の構成で「作業用」「配信用」を持つ。構成変化後の提案・自動適用(FR-12)と、トレイ・ホットキーの
  「配置を戻す」「現在の配置を保存」は**既定のプリセット**を使う。
- 理由: 同じモニタ構成でも用途(作業・配信・会議)で並べ方が違い、1構成1レイアウトだと保存し直すたびに前の並びが消える。
  ModeShift のモード切替(`layout.apply` + `preset`)と組み合わせる前提。
- 名前は構成の中で一意・40 文字以内。「自動」「抜く前」は自動スナップショット用に予約(利用者のプリセットには使えない)。

### データの形と移行

- `layouts/<sig>.json` を schema 2(`{"schema": 2, "signature", "monitors", "default": <id>, "presets": [{"id", "name", "saved_at", "windows"}]}`)にした。
  プリセットの `id` はファイル内で一意(`p1`, `p2`, …)で、名前を変えても変わらない。
- **v0.1 形式(schema 1)はそのまま読める**。読み込み時は「基本」という名前の既定プリセット1つとして扱い、ファイルは書き換えない。
- **初めて書くとき(保存・名前の変更・既定の変更など)に移行**する。移行の前に元ファイルを `<sig>.json.v1-backup-<日時>` に複製して残す(1回だけ)。
- 書くときは最上位に既定プリセットの `saved_at` / `windows` の写しも置く。v0.1 に戻しても既定プリセットは読める(読むときは `presets` が正)。
- 利用者のプリセットを上書き・削除するときは、書く前の中身を `<sig>.prev.json` に1世代残す(従来の FR-3 と同じ考え)。
- 壊れたファイルは従来どおり読まずにエラー。上書き保存時は `.broken-<日時>` に改名して残す。

### 画面

- 「プリセット」カード: 名前を付けて保存(同名は確認して上書き)・選択に上書き保存・計画(試運転)・適用・既定にする・名前を変更・削除。
- 削除は DeskKit 自身のデータなので、確認ダイアログを出したうえで行う。ファイルは消さず、外したプリセットを
  `<sig>.<id>.json.deleted-<日時>` に単体のレイアウトとして残す。最後の1つなら構成ごと `<sig>.json.deleted-<日時>` に改名する(C-8)。
  (仕様書の「レイアウトの削除 UI を作らない」は MODULE_GUIDE で撤回済み。)
- プリセットを選ぶとマップ・保存エントリ表・title_regex の編集がそのプリセットに切り替わる。
- 「保存済みレイアウト」表にプリセット数と既定の名前を出す。
- クイックアクション: 現在の構成のプリセットごとに「<構成名>: プリセット「<名前>」を適用」(試運転中は末尾に「(試運転)」)。
- CLI: `presets`(現在の構成のプリセット名)、`save [名前]`、`apply [名前]`、`plan [名前]`、`snapshot`。

### `layout.apply` の `preset`(契約 §2)

- `preset` があれば、**現在の構成シグネチャ**のプリセットを名前で探す。無ければ `result: "no_layout"`。
- `layout` に別の構成の名前・シグネチャが来たら、`preset` があっても `sig_mismatch`(INV-3)。
- `preset` を受けた要求の `layout.applied` には、結果にかかわらず受けた値をそのまま `"preset"` で返す(busy・error・wait_s 待ちの後も)。
  `preset` が無い要求には `preset` キーを付けない(従来どおり)。
- 文字列でない `preset` は `no_layout`(値はそのまま返す)。
- `preset: "自動"` / `"抜く前"` で自動スナップショットも指定できる(下の L2)。

## 2. L2 自動スナップショット

- 構成が**落ち着いてから `stable_min`(既定 10)分**たったら1回、以後**`interval_min`(既定 30)分ごと**に、対象(targets)のウィンドウ配置を
  `layouts/<sig>.auto.json` の「最新」に書く。確認は 1 分ごとの時刻比較だけで、列挙はしない。
- **同じ配置なら書かない**(hwnd・pid・起動時刻・show・normal_rect が同じ)。対象のウィンドウが 0 件なら書かない。書いたときだけ oplog に `snapshot` 行。
- **利用者のプリセットには触らない**(別ファイル)。
- 構成が動き出したとき(`WM_DISPLAYCHANGE` / 復帰の受信)に、直前の構成の「最新」を「抜く前」に写す。戻ってきた後の自動保存は「最新」だけを
  更新するので、崩れた配置で「抜く前」が上書きされない。
- 「抜く前の配置に戻す(自動保存)」をトレイと画面に置いた(「抜く前」が無ければ「最新」)。手で押す操作なので、試運転なら計画だけ・本番なら
  undo.json を書いてから適用(INV-6 / INV-7 のまま)。
- スヌーズ中・ゲーム/全画面(判定不能を含む)が前面の間は取らない(次の確認でまた試す)。
- **既定オンの理由**: 書くのは DeskKit のデータだけで、ウィンドウを動かさない(「新機能は既定オフ、または試運転から」の趣旨=自動で何かを
  動かさない、を満たす)。抜き差しの前の配置は後から取り直せないので、オフだと必要になったときに無い。書き込み頻度は最大でも 30 分に1回。
- タイトルは従来どおりレイアウトデータの `title_at_save` にだけ残し、ログ・oplog には書かない。
- 自動復元(構成変化後の提案・自動適用)は既定のプリセットだけを使い、自動スナップショットは使わない(利用者が選んだ配置だけを自動で提案する)。

設定(`settings.json` の `modules.layoutkeep`):

```json
"auto_snapshot": {"enabled": true, "stable_min": 10, "interval_min": 30}
```

範囲: `stable_min` 1〜240、`interval_min` 5〜1440(範囲外は丸める)。

## 3. L3 新しいウィンドウの配置

- **既定オフ・試運転から**。オンの間だけ `poll_ms`(既定 1500 ms)ごとに `EnumWindows` を呼び、前回との差分で新しいトップレベルウィンドウを見つける。
  **フック(イベントフック・ウィンドウフック)は使わない**。オフの間はタイマごと止め、EnumWindows も呼ばない。
- 新しい窓が無ければ 1 回の EnumWindows だけで終わる。新しい窓は、exe とクラスで targets に当たり得ないもの・オーナー付き・ツールウィンドウなら
  1回読んだら以後は見ない。見えて、位置が2回続けて同じになった(アプリ自身の位置合わせが済んだ)ときに判定する。15 秒で見えなければ諦める。
- 判定: 既定のプリセットに対して既存の対応付け(D-5 の決定表)を今の全対象ウィンドウで行い、その新しい窓が**一意に対応したとき(M-3 / M-4)だけ**
  保存位置へ置く。M-5(区別できない)・対応エントリ無し・既に保存位置なら動かさない(INV-2)。
- **1つの窓は1回だけ**。扱った hwnd を覚え、窓が消えたら忘れる(hwnd の再利用対策)。アプリが後から自分で動かしても追いかけない。
- 動かさない条件: スヌーズ中・ゲーム/全画面(判定不能を含む)が前面(このとき出てきた窓は中身を読まずに扱い済みにし、後からも動かさない)、
  対象のプロセスが昇格している/昇格状態を読めない(C-5)、構成変化の最中(判定を捨てて、落ち着いた後の窓を「既存」として覚え直す)。
- **試運転**: 「動かす予定」を画面の表・ログ・oplog(`place` 行 `result: dry_run`)に出すだけ。
- **本番**は `place_new.mode = "live"` **かつ全体の `mode = "live"`** のときだけ(INV-7: 全体が試運転の間は SetWindowPlacement を1回も呼ばない)。
  動かす前に undo.json を書き、書けなければ動かさない(INV-6)。連続して置いた窓は同じ undo.json に足すので、「直前の適用を元に戻す」でまとめて戻せる。
- 本番への切替は画面で確認ダイアログを出す。

```json
"place_new": {"enabled": false, "mode": "dry_run", "poll_ms": 1500}
```

`mode` が `live` 以外の値なら試運転として扱う(モジュールは止めない)。`poll_ms` は 1000〜10000。

## 4. スヌーズ(契約 §1)

`ctx.is_snoozed()` が True の間、次を止める。手で押した操作(トレイ・画面・ホットキー・クイックアクション・CLI)は止めない。

- 構成変化後の提案通知と自動適用(oplog に `suppressed` / `reason: "snoozed"`)
- 自動スナップショット
- 新しいウィンドウの配置(スヌーズ中に出てきた窓は後からも動かさない)

`layout.apply` イベントは止めない(下の「契約についての提案」)。本体が `is_snoozed` を持たない版で動いた場合は False として扱う。
画面の見出しとトレイの状態行に「一時停止中」を出す。

## 5. `diagnostics()`

件数・モード・真偽・理由コードだけを返す(タイトル・exe 名・パス・シグネチャは入れない)。

`disabled` `mode` `auto_apply` `targets` `invalid_targets` `signatures` `presets` `broken_layouts` `v1_layouts` `auto_snapshots`
`current_signature_known` `current_presets` `proposal_pending` `snoozed` `auto_snapshot` `place_new` `place_new_mode`
`place_pending` `last_apply` `last_snapshot` `last_place`

## 6. そのほかの修正

- **ワークスペース座標の換算を、ウィンドウが載っているモニタの作業領域で行うようにした**(不具合修正)。v0.1 は主モニタの作業領域のずれを
  全モニタに使っていたため、タスクバーを左・上に置いた副モニタでは、普通の窓を「スナップ中」と誤判定してずれた矩形を保存していた。
  取得(GetWindowPlacement)はスクリーン矩形が載るモニタのずれを引き、設定(SetWindowPlacement)は渡した矩形で MonitorFromRect したモニタの
  ずれを足す扱いにした(ReactOS の実装と PowerToys FancyZones の `ScreenToWorkAreaCoords` が同じ扱い)。実機での確認は未(§13 Q-15 のまま)。
- oplog の許可キーに `preset` `slot` を足した。新しい action: `snapshot` `place` `preset`(名前の変更・既定・削除)。
- `Win32Api` に `is_elevated(pid)` を足した(OpenProcessToken + TokenElevation を読むだけ。権限は変えない)。

## 7. 契約についての提案(自分では変えていない)

1. **`layout.apply` とスヌーズ**: 契約 §1 は LayoutKeep の「自動適用」を止める対象に挙げているが、`layout.apply` は ModeShift の手動切替からも
   来るため、LayoutKeep 側では区別できない。今回は止めていない(ModeShift の自動切替は ModeShift 側でスヌーズを見る前提)。区別が要るなら、
   `layout.apply` の payload に任意の `"auto": bool`(自動切替から来たか)を足す提案。
2. **自動スナップショットの `preset` 名**: `layout.apply` で `"自動"` / `"抜く前"` を予約名として受ける。ModeShift 側の入力欄で候補に出すなら、
   この2つが予約名であることを共有したい。
