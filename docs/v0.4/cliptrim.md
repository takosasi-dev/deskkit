# ClipTrim v0.4.0 — 仕様書からの変更点・既定値・実測値

対象: `deskkit/modules/cliptrim/**`・`tests/modules/cliptrim/**`。仕様書は `ClipTrim_動画の切り出し_仕様書.md`(T-* / FR-* / INV-* / AC-*)と、
末尾の「未確定事項への回答(2026-09-28、作者)」。回答が本文より優先(Q-2: 撮影場所などの情報は選択式、Q-5: 「送る」への登録を足す)。
逸脱不可要件(INV-1〜6・V4INV-1〜5)は変えていない。

## 1. ファイル

仕様書 §2 のとおり(`probe` / `keyframes` / `frames` / `plan` / `runner` / `jobs` / `oplog` / `page` / `module` / `selftest`)に、次を足した。

- `lanes.py`: 画面の裏の読み取りの通り道(コマ・まわりの読み取り・フィルムストリップ・開く、の各1本。T-12)。同じ鍵の新しい頼みが来たら、古い頼みと動いている子プロセスを捨てる。
- `config.py`: 設定の既定値と検証。
- `sendto.py` / `_win32.py`: 「送る」への登録(回答 Q-5)。SendPrep の `sendto.py` と `_win32.py` の `ShellLinkApi` / `RealShellLink` を写して名前だけ変えた
  (モジュールをまたいだ import はしない)。`_win32.py` にはビデオのフォルダ・ファイルの属性(クラウドだけの動画)・ドライブのファイルシステム名(FAT32)を足した。
- ffmpeg は本体の `deskkit.ffmpeg`(契約 §1.1)。`ffmpeg.shared().ensure()` と `check_h264()` は「開く」の通り道(GUI スレッドの外)で呼ぶ。

## 2. 仕様書からの変更点・解釈

| # | 内容 | 理由 |
|---|---|---|
| CT-1 | 映像は `-map 0:V:0`(大文字)で選ぶ。まわりの読み取り・コマ・書き出し・検証のすべて | 小文字の `v` はカバー画像(attached pic)も映像に数え、MP4 のカバー画像付きの録画で最初の映像がカバー画像になる。`V` は動いている映像だけ |
| CT-2 | 撮影場所などの情報は設定 `strip_metadata`(既定 `true` = 消す)。書き出しの欄に「消す / 残す」を毎回見える形で出し、変えたら保存する。本文の `keep_metadata` は使わない | 回答 Q-2。回転の情報は、画質そのままでは消す・残すのどちらでも入れ物に残る(P-11)。ぴったりでは回転を画素に反映するので、回転の情報そのものは無くなる(T-7・AC-6) |
| CT-3 | **MP4・MOV の実際の開始**: `-ss` を K ちょうどにして P-1 を読み直したとき、K より前の切れ目 L に着いても、実際の開始は K とする(試し直しはしない。MKV・WebM は T-5 のとおり) | 検体(kvazaar の HEVC、B フレームあり、K の pts−dts が 0.233 秒)で、ffmpeg が入力の前の `-ss` から 3/23 秒(0.13 秒)引いてシークするため、`-ss K` の P-1 の読み取りが1つ前の切れ目 L に着いた(P-5 と違う結果)。そのとき書き出した MP4 の中身は L から始まるが、K より前は編集リストで隠れ、ffmpeg でデコードした最初のコマは K だった(AC-3 の確かめ方)。T-5 の字のとおり L を実際の開始として出すと、AC-3 が通らず、編集リストを読むプレイヤーでの見え方とも違う。編集リストを読まないプレイヤーでは L から見える(§5 で実機確認) |
| CT-4 | FR-15 (c) の長さは、入れ物の長さではなく「映像のある長さ」(入れ物の終わり − 映像のストリームの開始)で見る | 画質そのままの MKV で、音声が映像の切れ目より 0.52 秒先に始まり(入れ物の長さに入る)、+1.0 秒の幅を超えた。画面の「長さ」は入れ物の長さのまま出す |
| CT-5 | AC-4 の「つなぐ ffmpeg の警告 0」は、**映像の警告 0** とした | B フレームのある HEVC の MP4 の2区間を concat すると、音声の包みの時刻が 18ms(1 包み未満)戻る警告が1行出た(`Non-monotonic DTS`。ffmpeg が直して書く)。区間の終わりで音声の包みが映像より少し長く残るため。デコードのエラー 0・コマの数が一時ファイルの合計と同じ、は満たす。H.264・MKV では警告 0 |
| CT-6 | AC-1 の「pts が負のパケットが無い」は映像の包みで確かめる | MP4 の音声には AAC の先頭の分(と B フレームのある元では最大約 1 秒)の負の pts の包みが入り、編集リストで隠れる。映像の包みは負にならない |
| CT-7 | ops.jsonl の `src_seconds` は元の動画の長さ | §9 に定義が無い(区間の合計は `out_seconds` と `segments` から分かる) |
| CT-8 | 「ぴったり」は `h264_mf` を確かめる前(開いた直後の数秒)も選べる。確かめて使えなければ「この PC では『ぴったり』が使えません」を出し、画質そのままに戻す | FR-9。確かめは開いた直後に裏で1回だけ行う(`deskkit.ffmpeg` が覚える) |
| CT-9 | フィルムストリップのコマを押したときは、区切りの中央ではなく **そのコマの実際の位置**(showinfo の pts_time)へ移る。読めなかったコマは1回だけ試し直す | 見えているコマと移った先のコマを一致させるため |
| CT-10 | タイムライン(スライダー)を引いている間は、60ms ごとに位置を決め、まわりの読み取りの通り道に 100ms の待ちを入れた(コマは T-4 の 150ms) | 引くたびに ffmpeg を起こして止めるのを減らす |
| CT-11 | ぴったりの音声は各本 AAC 128kbps で、チャンネル数は元のまま(`-ac` を付けない) | T-7 に指定が無い。5.1 の録画も持つ |
| CT-12 | FAT32 で 4GB を超える見積もりのときの ops の `result` は `error`(`no_space` は空き容量のときだけ) | §9 の結果コードに専用の物が無い |
| CT-13 | 区間の行に「移る」ボタン、動画の欄に「閉じる」(×)を足した。トレイに「ClipTrim を開く」 | FR-8 の「押すと開始へ移り」を行の中の小さなボタンでも押せるように。閉じるは区間を捨てるための入口 |
| CT-14 | 検証 (b)・(c)・(d)・(e) も BELOW_NORMAL・窓なし・`-protocol_whitelist file,pipe`・`file:` で呼ぶ(ffmpeg の呼び出しはすべて `runner.py` の Popen) | T-12・T-13 |
| CT-15 | 「送る」を足した(回答 Q-5)。設定の「エクスプローラーの『送る』に追加」をオンにしたときだけ `SendTo\ClipTrim で切り出す.lnk` を作る(リンク先は exe なら `DeskKit.exe cliptrim open`、ソース実行なら `pythonw.exe run_deskkit.py cliptrim open`)。オフで消すのは、リンク先が DeskKit で引数が `cliptrim open` の自分のショートカットだけ。起動のたびに、登録済みなら作り直す(exe の場所が変わったとき) | 回答 Q-5。仕様書 §3 の非スコープ「『送る』メニューへの登録」は回答で取り消し |
| CT-16 | AC-15 の grep に、`sendto.py` の自分のショートカットを消す `unlink` が1行かかる(理由のコメントつき)。ほかは `jobs.py` の `.part` の片づけ2か所だけ | 回答 Q-5 で「オフにしたら自分が作ったショートカットだけを消す」が加わったため |

### 設定(`modules.cliptrim`)の既定値

```json
{ "enabled": false, "mode": "copy", "output": "separate", "strip_metadata": true, "filmstrip_count": 24, "sendto_enabled": false }
```

型・範囲の合わない値は、その値だけ既定値に戻して書き戻す。知らないキーは残す。開いた動画のパスは覚えない。

### diagnostics() のキー(FR-19)

`ffmpeg`(`deskkit.ffmpeg` の状態)・`h264_encoder`(untested / available / unavailable)・`video_open`・`segments`(件数)・`mode`・`output`・
`strip_metadata`・`sendto`(registered / absent / other)・`busy`、最後のジョブの `last_mode`・`last_segments`・`last_result`・`last_seconds`。

### usage()(FR-18)

「切り出した本数」(primary、hint に R-2)・「画質そのまま」・「ぴったり」。どれも ops.jsonl の `files_ok` を日ごとに足した数。

### ログ・操作記録に書くもの(INV-3)

件数・秒・バイト数・結果コード・理由コード・例外の型名だけ。ファイル名・パス・ffmpeg の stderr は書かない(stderr の最後の1行は画面の結果の行にだけ出す)。
テスト `test_open_navigate_mark_and_export` で `秘密の録画_ab12.mp4` を開いて切り出し、ログ・ops.jsonl・diagnostics に「秘密の録画」も「ab12」も無いことを確かめている(AC-13)。

## 5. 実機で確かめること(仕様書 §8。この作業環境ではできなかったもの)

- 手に入る実物の録画(iPhone の縦・HDR の MOV、Android、OBS、Xbox Game Bar、NVIDIA、Zoom・Teams)の B フレームの有無・切れ目の間隔・まわりの読み取りの時間・早まり。
  特に **CT-3**: B フレームの深い MP4・MOV(iPhone の HEVC など)で `-ss K` の読み直しが前の切れ目に着くか。着いたとき、出力が「メディア プレーヤー」「フォト」・ブラウザで K から始まるか(編集リストを読むか)。
- 出力が「メディア プレーヤー」「フォト」とブラウザで頭から乱れずに再生できるか。開いた GOP(HEVC の CRA)の元の先頭の乱れ(P-8・Q-4)。
- キャッシュに無い 10GB 級で、位置を動かしてからコマが出るまで(10 回の中央値)。
- 60 分の 1080p60 のぴったりの時間と出力対元のビットレート(Q-3)。4K60 を `h264_mf` で作り直せるか(この PC の Media Foundation に依存する)。
- 書き出し・フィルムストリップの間に画面が 200ms 以上固まらないこと(v0.3 共通 NFR-4)。ffmpeg の呼び出しと検証はすべて GUI スレッドの外で、画面は QTimer と Qt のシグナルだけで更新している。
- 「送る」から開く(`DeskKit.exe cliptrim open <動画>`)。exe でのショートカットの中身(リンク先・引数)。
- OneDrive の「オンラインだけ」の動画で「クラウドにだけある動画です…」が出て、取り寄せが始まらないこと(属性 `RECALL_ON_DATA_ACCESS` / `OFFLINE` は偽物でだけ確かめた)。
- 出力先が FAT32 の USB メモリで 4GB を超える見積もりのとき、書き出しを始めないこと(ファイルシステム名は偽物でだけ確かめた)。

## 6. 契約変更の提案

- `deskkit.ffmpeg.FfmpegManager.check_h264()` の子プロセスは優先度が通常のまま。ClipTrim の T-12 は ffmpeg を BELOW_NORMAL で動かす決まりなので、本体の `check_h264` にも
  `BELOW_NORMAL_PRIORITY_CLASS` を足すと揃う(数フレームだけなので実害は小さい)。

### 対応(2026-09-29、統合のとき)

- `FfmpegManager.check_h264()` の子プロセスに `BELOW_NORMAL_PRIORITY_CLASS` を足した(`deskkit.ffmpeg.BELOW_NORMAL_PRIORITY_CLASS`)。
