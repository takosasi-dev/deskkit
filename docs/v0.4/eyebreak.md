# EyeBreak v0.4.0 — 仕様書からの変更点と実測値

対象: `deskkit/modules/eyebreak/**`。EyeBreak 実装仕様書 v1・v0.4 共通仕様書・`docs/MODULE_GUIDE.md`・`docs/INTERFACES_v0.4.md` からの差分と、§8 の実測値だけを書く。
逸脱不可要件(INV-1〜INV-6・V4INV-1〜5)は変えていない。起動したときの ModeShift のモードを返す API は足していない(V4Q-3 は今の案で確定。E-9 のとおり起動時は「静かにするモードではない」)。

## 1. ファイル構成(§2 からの追加)

| ファイル | 役割 |
|---|---|
| `config.py` | §9 の設定の読み取り。足りないキーは既定値で補って書き戻し、型・範囲の合わない値は `EyeBreakSettingsError`(共通基盤 D-9: host がこのモジュールだけ停止中にする) |

`_win32.py` にはテストと自己検査のための `FakeApi` も置いた(入力なしの秒数を直接決める)。

## 2. 変更点・解釈

| # | 内容 | 理由 |
|---|---|---|
| E-a | `ctx.notify(..., replace_key="eyebreak.prompt")` で呼び、`TypeError` が出たら **1回だけ** replace_key なしで呼び直し、以後は付けない(`diagnostics()` の `replace_key` が false になる) | 契約 §2.2 の本体の変更(H4-6)が入る前の本体でも動くように(依頼の指示) |
| E-b | 続けて使った時間は `start()` の時刻から数える(最初の読み取りの 5 秒も数える) | 最初の読み取りを起点にすると、20 分の声かけが 5 秒遅れるため |
| E-c | 1回の読み取りで進める時間は最大 60 秒 | タイマーが遅れた・スリープから戻ったときに、止まっていた時間を「使っていた」と数えないため(スリープ中に tick が進むかは未確認。§4) |
| E-d | 保留(ゲーム・全画面・静かにするモード)を出すまでの `after_game_delay_s` は、「安全になった」と初めて読んだ回の **直前の読み取りの時刻** から数える | 5 秒ごとにしか読まないので、抜けた時刻は直前の読み取りの直後とみなす。AC-4 の「30 秒で出る・29 秒で戻ると出ない」がそのまま成り立つ |
| E-e | `game: "pause"` のときも、声かけ(「10分あとで」の再度の声かけなど)の時刻にゲーム中・全画面なら保留にする。そのときの文言は「ゲームのあと」ではなく普通の文言 | INV-2(ゲーム中・全画面は notify を呼ばない)と §10「10分あとで の時刻にゲーム中 → 保留」。pause では数えを止めているので「ゲームを含めて」は当たらない |
| E-f | 「今日はもう出さない」の間も、間隔に達したら数えを 0 に戻す(ログは `prompt kind=… result=muted`) | 止めている間に数えが伸び続けると、朝 4 時に解けた瞬間に声がかかるため。ログの `result=muted` はこのために使う |
| E-g | 「休めた」(E-5)は、声かけを出した時刻より後の入力なしだけを数える。止まり始めが期限(3 分・15 分)以内なら、期限を過ぎてから 20 秒・`break_idle_min` に達しても数える | 声かけの前から手が止まっていた分を「休めた」にしないため。「3 分以内に止まった」を素直に読んだ |
| E-h | 一時停止は `host.snooze_changed` に加えて、5 秒ごとの読み取りでも `ctx.is_snoozed()` を見る。解けたら 0 から数え直し、保留と「あとで」も取り消す | QUNS 連動(H2)の一時停止ではイベントが来ない場合に備えて。FR-11 |
| E-i | トレイ・CLI の「10分あとで」は、最後に作った声かけの種類(無ければ目)で予約する。「あとで」を押すたびに `daily.json` の `later` を 1 足す | 仕様書は窓から押す場合しか種類を書いていないため |
| E-j | 画面の「間隔」のカードに、`break_idle_min`・`later_min`・`day_start_hour` の行を、「ゲームのとき」のカードに `after_game_delay_s` の行を足した。画面から範囲外の値を入れると保存せず、理由を出す | §9 の設定をすべて画面から変えられるように(MODULE_GUIDE §0) |
| E-k | トレイの状態(FR-17)は次の順で1つ: 読めない > 一時停止中 > 今日は止めています > ゲームのあとで出します > 静かにするモードの間は待っています > 様子見中 > 「目 12分・体 38分」。目・体の片方を切っていればその分は出さず、両方切っていれば「声かけはすべてオフです」 | §10 の「静かにするモードの間は待っています」も出せるように |
| E-l | トレイの「再開する」は、今日は止めているか「あとで」の予約があるときだけ押せる。クイックアクションは FR-18 のとおり | 押しても何も変わらない状態を避けるため |
| E-m | 前面の読み取り(`ctx.foreground()`)は、`game: "after"` では声かけを作るときと保留がある間だけ、`"pause"` では毎回 | FR-9・FR-10。前面が DeskKit 自身のときは、本体が `is_game=False`・`is_fullscreen=False` を返すので、仕様書どおり声をかける(特別扱いしない。依頼の指示) |
| E-n | ModeShift の今のモード名はメモリにだけ持ち(書かない。INV-4)、設定の `quiet_modes` を変えたらすぐに判定し直す。`restored: true` の `modeshift.switched` も普通の切り替えとして扱う | INTERFACES_v0.2 §2 |
| E-o | 声かけの窓は通知のクリックでだけ開き、開いていた窓があれば閉じてから開く。非モーダル | FR-5・INV-3 |
| E-p | 「今日はもう出さない」の知らせの文は「明日の朝4時まで出しません。…」。0〜3 時に押したときは「今日の朝4時まで」。`day_start_hour` が 4〜11 なら「朝N時」、それ以外は「N時」 | FR-7 の文を `day_start_hour` と押した時刻に合わせるため |
| E-q | 「いま続けて使っている時間」は、最後に休んでから使っている時間(声かけで 0 に戻らない) | 目・体の数えは声かけごとに 0 に戻るので、利用者の感覚と合わないため |

### ログに書くもの(INV-4・§9)

§9 の `prompt kind= result=`・`rested kind=`・`break`・`mute`・`resume`・`idle_unavailable` のほかに、`eyebreak start mode= game=`・`eyebreak stop`・`notify replace_key unsupported`・`daily broken` / `state broken`(§10)・書き込みの失敗(例外の型名だけ)。exe 名・ウィンドウの題・モード名は書かない(`test_ac14_*` で確かめている)。

### diagnostics() のキー(FR-21)

`mode`・`idle_readable`・`game`・`quiet_modes`(数)・`muted_today`・`replace_key`・`prompts_14d`・`rested_14d`・`later_14d`・`mute_today_14d`。

## 3. 決めた既定値

§9 のまま(様子見・目 20 分・体 60 分・休んだとみなす 5 分・あとで 10 分・`after`・30 秒・`quiet_modes` 空・4 時)。追加の定数: 3 回続けて読めなければ「読めません」(FR-1)、1回の読み取りで進める最大 60 秒(E-c)。

## 4. §8 の実測(2026-09-28、この PC: Windows 11 Pro 10.0.26200・ソース実行)

- `GetLastInputInfo` は管理者でない利用者で読めた。手を触れずに 1.2 秒待つと、入力なしの秒数が 1 秒以上増えた(`tests/modules/eyebreak/test_real.py`、`win32_real`)
- 本物の host(一時フォルダの DESKKIT_HOME)で有効にして起動し、`running`・`diagnostics()` の `idle_readable: true`・画面と声かけの窓を開けることを確かめた
- **NFR4-3(5 秒ごとの読み取りの CPU 時間)**。本物の `GetLastInputInfo` と、偽の ctx(前面は常に安全・様子見)で測った(使い捨てのスクリプト。2026-09-28):
  - (a) 1 回の読み取り(`tick()`: 入力なしの秒数・判定・画面への合図)の CPU 時間を 5,000 回の平均で: **3.1 µs / 回**。1 時間(720 回)に換算して **約 2.3 ms**
  - (b) 本物の 5 秒のタイマーで **5 分間**(60 回)動かしたプロセスの CPU 時間: タイマーなしで 5 分待った場合 0.0 ms、EyeBreak ありで 15.6 ms(差 15.6 ms、1 時間に換算 約 190 ms)。ただし Windows の `time.process_time()` の刻みは 15.6 ms なので、(b) は「1 刻み分以下」としか言えない。Qt のタイマーで起きる分を含めても、1 時間で 0.2 秒程度を上限の目安とみなしてよい
  - 声かけを作るときだけ読む `ctx.foreground()` の分と、通知・`daily.json` の書き込みの分は含まない(1 時間に 1〜3 回)

## 5. 実機で確かめること(未実施)

- AC-17 の後半: 手を止めると秒数が増え、マウスを動かすと 1 秒未満に戻ること(人の操作が要る)

- `game_processes` のゲームを全画面・ボーダーレスで動かしたとき、ブラウザの動画を全画面にしたときの `is_game`・`is_fullscreen`
- Windows の集中セッション中に `ctx.notify` が保留(H1)されるか、解けたときに EyeBreak の通知が何通出るか(本体の H4-6 が入った後で replace_key が効くこと)
- 5 秒ごとの読み取りを **1 時間** 続けたときの CPU 時間(上は短い時間の値)
