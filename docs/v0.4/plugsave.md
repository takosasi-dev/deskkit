# PlugSave v0.4.0 — 仕様書からの変更点・既定値・実測値・実機で確かめること

対象: `deskkit/modules/plugsave/**`。PlugSave 実装仕様書 v1(2026-09-28)と、その末尾の「未確定事項への回答」(Q-1〜Q-7 はすべて今の案のまま)、
v0.4 共通仕様書・`docs/MODULE_GUIDE.md`・`docs/INTERFACES_v0.4.md` からの差分を書く。
逸脱不可要件(INV-1〜INV-7・V4INV-*・VINV-*)は緩めていない。設定(§9)と ops.jsonl の項目は仕様書のとおり。

## 1. ファイル構成

仕様書 §2 のファイルに次の1つを足した。

| ファイル | 役割 |
|---|---|
| `fakes.py` | 偽の Win32(`FakeDriveApi`)。ドライブの「根」を一時フォルダにし、種類・ボリューム情報・空き容量を決めて返す。呼ばれた回数も数える(AC-9)。テストと自己検査が使う(StartupWatch の `fakes.py` と同じ置き方) |

- `_win32.py` の `DriveApi` に `root(letter)`(本物は `"E:\"`、偽物は一時フォルダ)と `disk_usage(root)`(`shutil.disk_usage`)を足した。
  ドライブの中のパスはすべてこの根から作るので、テストは本物のドライブに一切触れない。
- 消す処理(`os.remove` / `os.rmdir`)は `staging.py` の2行だけ(AC-20)。どちらも消す前に名前の形(`<数字>.part`・`plugsave_id.<32桁>.part`・
  `readme.<32桁>.part`・32 桁の 16 進の回のフォルダ)を確かめる。`copier.py` と `drives.py` は `staging.discard_part` を呼ぶ。
- `os.replace` と `shutil.copy*` は使わない(AC-21)。最終の名前へは `os.rename`(同じ名前があると失敗する)だけ。

## 2. 仕様書から外れた点・決めたこと

| # | 内容 | 理由 |
|---|---|---|
| S-1 | 印(`plugsave_id.json`)と「はじめにお読みください.txt」の一時ファイルは `plugsave_id.<32桁>.part` / `readme.<32桁>.part`。名前の変更に失敗したときは `staging.discard_part` で消す | AC-20 は消す処理を staging.py と copier.py の「自分の .part」に限っている。印の一時ファイルもその形にそろえた |
| S-2 | 壊れた印を登録し直すとき(§10)、壊れた印は消さず、`DeskKitバックアップ\_以前の版\<日時>\plugsave_id.json` へ名前の変更で移してから新しい印を書く | 「新しい ID で印を書き直す」を上書きなしで行うため。INV-2 の「既存のファイルに行うのは _以前の版 への名前の変更だけ」に合わせた |
| **S-3** | **FR-15 の 300,000 の上限は「コピーが要るファイル(新しい・変わった)」の数で数える。「そのまま」と「飛ばす」は数えない**(仕様書は「そのまま」を含む) | 「そのまま」を含めて数えると、30 万を超えるコピー元では毎回同じ先頭の 30 万件(2回目からは全部「そのまま」)で切れ、残りが**永久に**コピーされない。「残りは次の回にコピーします」を本当にするため。AC-16(8 件・上限 5 → 5 件で切れる)はこのままで満たす。走査そのものは全部たどるので、ファイルが極端に多いと計画に時間がかかる |
| S-4 | `first_done` は、初回の回が **ok で終わったとき** に真にする(「始める」を押しただけでは真にしない) | 初回が途中で外れた・空きが足りないときに、次に挿すと確かめずに自動で始まるのを避ける(安全な側) |
| S-5 | 「入る分だけコピー」は、更新日時の新しい順に並べ、**最初に入らなかったところで止める**(それより古い小さいファイルは取らない)。入らなかった物が残った回の結果は `no_space`(成功として日数を数え直さない) | 「新しい順に入るだけ」を、新しい方から途切れなく取る意味にした。全部を取れていない回を成功にすると、思い出させる通知が止まる |
| S-6 | トレイの状態の行: 実行中は「バックアップ中 n%」、待ち時間中・ゲーム待ち・初回の計画を作っている間は「待機中」、それ以外は「最後のバックアップ: N 日前」(0 日は「最後のバックアップ: 今日」)/「まだバックアップしていません」 | FR-26 の4つの文言の使い分けを決めた。「0 日前」は読みにくいので「今日」にした |
| S-7 | ドライブが外れた(`DBT_DEVICEREMOVECOMPLETE`)ら、その文字の「30 秒以内の合図は無視」を解く | 抜いてすぐ挿し直したときに無視しないため。30 秒の窓は同じ挿し込みで何回も届く合図のためのもの |
| S-8 | 待ち時間が終わったときにも一時停止とゲーム・全画面を確かめ直す。一時停止なら取りやめ、ゲーム中なら 30 秒ごとの確認に戻る | 待ち時間の間にゲームを始めた場合に、取り消せないまま始まらないように(B-11 の趣旨) |
| S-9 | 初回が済んでいないドライブの通知(FR-10)は、ゲーム・全画面中なら出さない(待ちもしない) | FR-10 の「B-11 に当たるときを除く」。後で出す仕組みは足していない(画面の「計画を作る」から始められる) |
| S-10 | ops.jsonl の `skipped` は `write_failed`・`old_version_move_failed` を除いた理由ごとの数、`failed` はその2つの合計。完了の通知の「飛ばした M 件」は飛ばし + 失敗の合計。コピー 0 件で飛ばしがあるときは「変わったファイルはありませんでした・飛ばした M 件」 | §9 の理由コードに失敗の2つが入っているため、どちらに数えるかを決めた。画面の表には両方を理由つきで出す |
| S-11 | 「やめる」から 5 秒で戻らないとき(FR-20・§10 壊れかけのドライブ)は、止まった扱いにして「ドライブの応答がありません」を出し、ops に `cancelled`(件数は 0)を1行残す。そのスレッドが生きている間は次の回を始めない(同じ文言を返す) | 戻らないスレッドと新しい回が同じドライブに同時に書くのを避ける |

## 4. 実測値

- 構造体(この PC の Python 3.13・64bit の ctypes): `DEV_BROADCAST_HDR` 12 バイト、`DEV_BROADCAST_VOLUME` 20 バイト、`dbcv_unitmask` は位置 12、`dbcv_flags` は位置 16(`test_struct_layout`)。
- この PC のドライブ(`test_real.py`、読むだけ): C: は種類 3(FIXED)・NTFS、D: は種類 2(REMOVABLE)・exFAT。
- **fsync を1ファイルごとに呼ぶ影響(§8。報告)**: 一時フォルダ(システムドライブの NTFS、SSD)で 10,000 ファイル・合計 約 100MB(1 個 10KB)を、
  本物の部品(`BackupRun`)でコピーした(`test_measure_real.py`)。

  | | 初回 | 変更なしの2回目 |
  |---|---|---|
  | 1ファイルごとに fsync(仕様どおり・今の実装) | **171.2 秒**(1 ファイル 約 17ms) | 0.15 秒 |
  | fsync なし(比べるためだけ) | 34.7 秒(1 ファイル 約 3.5ms) | 0.10 秒 |

  小さいファイルが多いと、fsync だけで初回が **約 5 倍** 遅くなる。USB メモリではさらに遅いと見込む(実機で測る)。
  仕様どおり1ファイルごとの fsync のままにしてある。抜かれても最終の名前に壊れたファイルができない、という B-8 の保証の要なので、変えるかは利用者の判断(§7)。
- 2回目(変更なし)は、先のフォルダを1フォルダにつき1回 `scandir` して比べるので、10,000 ファイルで 0.15 秒。
- NTFS へコピーして `os.utime` で合わせたあとの更新日時の差: 1ms 以内(`test_new_changed_deleted_and_source_untouched` で確かめている)。**FAT32・exFAT の差は測っていない**(D: に書かないため。§5)。
- OneDrive の「オンラインだけ」のファイルの `st_file_attributes`: この PC の OneDrive にはオンラインだけのファイルが無く(ファイル 1 個、属性 0x26)、**測れなかった**(§5)。
  判定は `OFFLINE`・`RECALL_ON_OPEN`・`RECALL_ON_DATA_ACCESS` のどれか(FR-14)で、偽の項目で AC-6 を確かめた。

## 5. 実機で確かめること

どれも本物のドライブへの書き込みを伴うため、今回は行っていない(依頼の指示: 利用者のドライブに書き込まない)。

1. **隠しウィンドウに `WM_DEVICECHANGE` が届くか(仕様書 §2「本体に頼むこと」・§8 の1つ目・AC-23)**: USB メモリと外付け SSD(か HDD)を挿して、
   `wParam`・`dbch_devicetype`・`dbcv_unitmask`・`dbcv_flags`、届くまでの秒数、同じ挿し込みで届いた回数を記録する。ログには
   `registered drive arrived slot=… serial_match=…` が出る(文字・ラベルは出ない)。登録していないドライブでは何も出ないこと。
   届かなければ PlugSave では回避せず、本体の担当へ報告する(仕様書 §2)。
2. 2つの `GetDriveTypeW` の値(USB メモリは 2、外付け SSD・HDD は 3 の見込み)とファイルシステム名。
3. FAT32 と exFAT のドライブへコピーして `os.utime` で合わせたあとの、コピー元との更新日時の差の最大(ns)。2 秒の幅(B-6)に収まり、2回目が全部「そのまま」になること。
4. 10,000 ファイル・合計 1GB の初回と、変更なしの2回目の所要時間(USB メモリと SSD)。fsync の影響(§4)を USB メモリでも見る。
5. BitLocker To Go のドライブの鍵を開けたとき、`DBT_DEVICEARRIVAL` がもう一度届くか。ロックしたまま挿したときに何も起きないこと(§10)。
6. OneDrive の「オンラインだけ」のファイルの `st_file_attributes`(16進)と、`cloud_only` で飛ばされ、ダウンロードが始まらないこと。
7. 書き込み禁止のスイッチのある SD カード・USB メモリで「書き込めません。…」が出ること(`_作業中` を作れず `error`)。
8. コピーの途中で USB メモリを抜いて `removed`(「バックアップの途中でドライブが外れました。…」)になり、挿し直した次の回の始めに `.part` が片づくこと(FR-21・FR-22)。
9. 単体 exe(PyInstaller)で 260 文字を超えるパスをコピーできること(ソース実行ではテストで確かめた。先のパスは `\\?\` 付きで扱う)。
10. スリープからの復帰でドライブが外れた扱いになったとき、`removed` で終わること。

## 7. 利用者に聞くべきこと

1. **fsync を1ファイルごとに呼ぶか**(§4 の実測で、小さいファイルが多いと初回が約 5 倍遅い)。今の案(仕様どおり)のままか、たとえば「一時ファイルは fsync せずに書き、
   回の終わりに1回まとめて同期してから最終の名前にする」などに変えるか。変えると、抜かれたときに最終の名前の壊れたファイルが残りうる時間が長くなる。
2. **S-3(300,000 の上限の数え方)** をこのままでよいか。仕様書のとおり「そのまま」も数えると、30 万ファイルを超えるコピー元で残りが永久にコピーされない。
3. S-4(初回が ok で終わったときだけ「初回が済んだ」とする)でよいか。

### 回答(2026-09-29、統合のとき)

1. **速さを取る**。ただし「回の終わりにまとめて同期」は、開き直して fsync するぶん1件ずつより遅かった(一時フォルダの NTFS・SSD で 10KB × 2,000 件: 1件ずつ fsync 5.5 秒 / 書いたあとで開き直して fsync 23.3 秒 / fsync なし 0.5 秒)。
   ボリューム全体の確定(ボリュームのハンドルへの FlushFileBuffers)は管理者が要る。そこで **1MiB 未満のファイルは fsync しない**(`copier.FSYNC_MIN_BYTES`)。1MiB 以上は今までどおり1件ずつ fsync する。
   小さいファイルは抜かれたときに最終の名前のまま中身が欠けることがありうる(次の回は大きさと更新日時で比べるので気づかない)。利用者はこれを受け入れた。
2. 今の案のまま。
3. 今の案のまま。
